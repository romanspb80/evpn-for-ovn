# EVPN-for-OVN v0.1.0 Experimental

EVPN-for-OVN v0.1.0 provides experimental Netlink-Programmed integration of
EVPN Type-2 routes with OVN-based workloads. It is not production-qualified.

## Scope and included functionality

GoBGP is the selected BGP/EVPN control-plane engine. OVN/OVS is the intentional
workload networking foundation and forwards workload packets. Linux Netlink
reconciles integration state consumed by OVN/OVS; it is not an independent
Linux-bridge workload dataplane.

The release includes Type-2 route processing, advertisement and withdrawal,
owned endpoint lifecycle, authorization, fencing and durable recovery state.
Node-Agent and speaker restart handling are part of the experimental
implementation, not a general availability guarantee. External EVPN route
exchange and OVN/OVS-to-external-VTEP VXLAN forwarding remain distinct.

The primary validated networking use case is Two-Chassis EVPN Type-2
Connectivity: two OVN/OVS chassis with a shared NBDB/SBDB control plane, GoBGP
route exchange and VXLAN data-plane forwarding. Independent OVN-domain
interconnection remains planned; general vendor interoperability remains
experimental.

Deployment and orchestration, workload integration, network-state programming,
platform integration and the BGP/EVPN control plane are separate dimensions; this release does
not promise every possible combination. Standalone Node-Agent EVPN
import/export paths do not require the Operator and do not start a CNI server.
Kubernetes CNI/Multus provides secondary attachments, and the Operator
manages its constrained Kubernetes core profiles. Multi-worker examples
describe node-local inventory and ownership boundaries; they do not establish
generalized multi-VTEP lifecycle support. GoBGP is the BGP/EVPN engine;
optional `k8gobgp` supplies Kubernetes speaker-provider integration, and the
Operator currently accepts no other provider.

Direct OVSDB-Programmed integration remains available for maintenance and
tests only, outside the selected v0.1.0 deployment scope. OVN-Kubernetes and
Neutron / ML2-OVN integrations remain planned. Type-3 and Type-5 functionality
are outside this Type-2 release scope.

## Security and operations

Real OVN/OVS plus Linux-veth CNI transport requires root:root Unix peer
authentication, independently of optional continuity configuration.
Standalone export requires protected administrator authorization, durable
fencing, OVN identity checks and speaker attestation.

The supported Operator Netlink profile excludes legacy unauthenticated
management services and does not enable the benchmark-only provenance bypass.
Legacy Kind compatibility services remain unauthenticated to permitted
in-cluster callers; ClusterIP is not authentication. See
[SECURITY.md](../../SECURITY.md) for trust boundaries.

## Known limitations

- Missed CNI DEL/orphan recovery and Kubernetes API-unavailability recovery
  have incomplete operational acceptance.
- Arbitrary pre-existing foreign-state preservation and generalized
  multi-VTEP lifecycle are not release guarantees.
- Production availability, upgrades, rollback and broad platform support
  are outside the qualified scope.
- Advanced direct-OVSDB restart/withdrawal scenarios and OVSDB
  regressions remain deferred.

## Release acceptance

The maintainer reports that all tests in the final revised acceptance
inventory passed before publication. The revised inventory, exact tested
source revision and final evidence bundle are not included in this repository,
so this release note does not assert a numeric test count. The
[validation-history archive](../internal/validation-history/README.md)

maintainer-provided final status.

Do not deploy this release as a production network platform or infer
production readiness from implemented recovery paths or example topologies.
